# Chapter 7 分析

## Q1: FIFO vs SJF vs RR (q=1)，工作负载 100,200,300

### 命令

```bash
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p FIFO -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p SJF -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p RR -q 1 -c
```

### 结果汇总

| 策略 | 平均响应时间 | 平均周转时间 |
|------|--------------|--------------|
| FIFO | 133.33 | 333.33 |
| SJF | 133.33 | 333.33 |
| RR (q=1) | 1.00 | 465.67 |

### 分析

1. **FIFO 与 SJF 结果相同**：作业列表 100,200,300 已按长度升序给出，FIFO 的执行顺序恰好等于 SJF 的最优顺序。SJF 的优势只有在长作业先到达时才能体现（例如列表为 300,200,100 时）。

2. **RR 的响应时间远优于 FIFO/SJF**：RR 让每个作业尽快获得首次运行，平均响应时间仅 1.00，而 FIFO/SJF 为 133.33。这是抢占式调度在公平性/响应性上的优势。

3. **RR 的周转时间反而更差**：RR 的平均周转时间为 465.67，高于 FIFO/SJF 的 333.33。因为 RR 频繁切换，短作业也被拉长完成时间。RR 用周转时间换取了响应时间。

4. **重要观察**：作业 0 在 t=298 完成后，队列只剩作业 1 和作业 2，RR 的轮转从 3 个作业变成 2 个作业，剩余作业的推进速度加快——这是预测 RR 周转时间时容易忽略的细节。

## Q2: 随机工作负载 (seed=1)，FIFO vs SJF vs RR (q=1)

### 命令

```bash
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p FIFO -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p SJF -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p RR -q 1 -c
```

### 工作负载

seed=1 生成 3 个作业（默认 -j 3，-m 10，同时到达）：
- Job 0：长度 2
- Job 1：长度 9
- Job 2：长度 8

### 结果汇总

| 策略 | 平均响应时间 | 平均周转时间 |
|------|--------------|--------------|
| FIFO | 4.33 | 10.67 |
| SJF | 4.00 | 10.33 |
| RR (q=1) | 1.00 | 13.67 |

### 分析

1. **SJF 略优于 FIFO**：SJF 先跑最短的 Job 0(2)，再跑 Job 2(8)，最后 Job 1(9)。周转 10.33 < 10.67。

2. **RR 响应时间最优但周转最差**：响应时间 1.00（三个作业在 t=0,1,2 都获得首次运行），周转时间 13.67，比 FIFO/SJF 都差。

3. **RR 的推演细节**：
   - Job 0 在 t=0,3 各跑 1 单位，t=4 完成，周转 4
   - Job 0 完成后只剩 J1、J2 交替，每 2 个时间单位各跑 1 单位
   - Job 2 在 t=17 开始最后 1 单位，t=18 完成，周转 18
   - Job 1 在 t=18 开始最后 1 单位，t=19 完成，周转 19
   - 平均 = (4 + 19 + 18) / 3 = 13.67

4. **RR 用周转时间换响应时间**：这是抢占式调度的典型权衡。
## Q3: RR 使用不同 quantum（工作负载 seed=1，作业长度 2, 9, 8）

### 命令

```bash
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p RR -q 1 -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p RR -q 5 -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -s 1 -p RR -q 10 -c
```

### 结果汇总

| quantum | 平均响应时间 | 平均周转时间 |
|---------|--------------|--------------|
| 1 | 1.00 | 13.67 |
| 5 | 3.00 | 12.33 |
| 10 | 4.33 | 10.67 |

### 分析

1. **quantum 越大，响应时间越差**：q=1 → 1.00，q=5 → 3.00，q=10 → 4.33。quantum 越大，作业等待首次运行的时间越久，公平性下降。

2. **quantum 越大，周转时间越好**：q=1 → 13.67，q=5 → 12.33，q=10 → 10.67。quantum 越大，上下文切换越少，作业完成得更快。

3. **q=10 时 RR 退化为 FIFO**：因为 quantum 10 已大于所有作业长度（2、9、8），每个作业一旦开始就运行到底，RR 的行为与 FIFO 完全相同。结果也与 Q2 中的 FIFO 一致（响应 4.33，周转 10.67）。

4. **结论**：quantum 的选择是响应时间与周转时间之间的权衡。quantum 太小 → 响应好但切换开销大、周转差；quantum 太大 → 周转好但响应差，极端情况退化为 FIFO。OSTEP 的建议是 quantum 应足够大以摊销切换开销，但又足够小以保持响应性。
## Q4: 量子大小与上下文切换开销（工作负载 100,200,300）

### 命令

```bash
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p RR -q 1 -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p RR -q 10 -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p RR -q 100 -c
```

### 结果汇总

| quantum | `Run job` 行数 | 平均响应时间 | 平均周转时间 |
|---------|----------------|--------------|--------------|
| 1 | 600 | 1.00 | 465.67 |
| 10 | 60 | 10.00 | 456.67 |
| 100 | 6 | 100.00 | 366.67 |

### 分析

1. **quantum 越大，切换次数越少**：q=1 时切换 600 次，q=10 时 60 次，q=100 时 6 次。切换次数 ≈ 总工作量 / quantum。总工作量 = 100 + 200 + 300 = 600，600/1=600，600/10=60，600/100=6。

2. **切换次数与响应时间成反比**：q=1 响应 1.00，q=10 响应 10.00，q=100 响应 100.00。quantum 越小，作业越早获得首次运行，响应时间越好。

3. **切换次数与周转时间成正比方向相反**：q=1 周转 465.67，q=10 周转 456.67，q=100 周转 366.67。quantum 越大，周转时间越好。

4. **结论**：上下文切换有开销。如果每次切换耗时 c，总切换开销 ≈ (总工作量 / quantum) × c。quantum 太小会导致大量切换开销，浪费 CPU；quantum 太大则响应变差。OSTEP 建议 quantum 应足够大以摊销切换开销，但又足够小以保持响应性。
## Q5: quantum 与周转时间的最优点（工作负载 100,200,300）

### 命令

```bash
for q in 1 5 10 20 50 100 200 300; do
  echo "=== quantum=$q ==="
  python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 100,200,300 -p RR -q $q -c | grep Average
done
```

### 结果汇总

| quantum | 平均响应时间 | 平均周转时间 |
|---------|--------------|--------------|
| 1 | 1.00 | 465.67 |
| 5 | 5.00 | 461.67 |
| 10 | 10.00 | 456.67 |
| 20 | 20.00 | 446.67 |
| 50 | 50.00 | 416.67 |
| 100 | 100.00 | 366.67 |
| 200 | 133.33 | 333.33 |
| 300 | 133.33 | 333.33 |

### 分析

1. **quantum 越大，平均周转时间越低**：从 q=1 的 465.67 一路降到 q=200 的 333.33。当 quantum ≥ 最大作业长度（300）时，RR 不再发生抢占，退化为 FIFO，周转时间达到最小值 333.33。

2. **quantum 越小，平均响应时间越好**：q=1 时响应 1.00，q=300 时响应 133.33。响应时间与 quantum 近似成正比（响应 ≈ quantum / 2 附近）。

3. **最小值出现在退化点**：当 quantum ≥ 最大作业长度时，RR 不再发生任何抢占，行为和 FIFO 完全相同。此时平均周转时间最小（333.33），但响应时间最差（133.33）。

4. **结论**：从周转时间角度看，最优 quantum 是"不小于最大作业长度"的值（即退化到 FIFO）。但这样会牺牲响应时间。实际系统中需要在两者之间取折中，quantum 通常设为几十毫秒。
## Q6: Convoy Effect（护航效应），工作负载 300,100,200

### 命令

```bash
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 300,100,200 -p FIFO -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 300,100,200 -p SJF -c
python3 ./ext/ostep-homework/cpu-sched/scheduler.py -l 300,100,200 -p RR -q 1 -c
```

### 结果汇总

| 策略 | 平均响应时间 | 平均周转时间 |
|------|--------------|--------------|
| FIFO | 233.33 | 433.33 |
| SJF | 133.33 | 333.33 |

### 分析

1. **护航效应**：FIFO 先执行长作业 Job 0（300），Job 1（100）和 Job 2（200）被迫等待。Job 1 的响应时间高达 300，Job 2 的响应时间高达 400——短作业被长作业"护航"阻塞。

2. **SJF 消除护航效应**：SJF 重排执行顺序为 Job 1(100) → Job 2(200) → Job 0(300)。短作业先运行，Job 1 响应时间降到 0，Job 2 降到 100。平均响应时间从 233.33 降到 133.33。

3. **平均周转时间对比**：FIFO 433.33，SJF 333.33。SJF 比 FIFO 少 100。注意：SJF 让最长的 Job 0 最后一个完成，但整体平均周转时间反而更优。这就是 SJF 的"最优性"。

4. **结论**：护航效应是 FIFO 的典型缺陷——先到的长作业阻塞了后续短作业。SJF 通过优先运行短作业消除这个效应，同时最小化平均周转时间。代价是长作业可能饥饿。
## Q7: SJF 的最优性推导

### 问题

给定 n 个作业，长度分别为 L₁, L₂, ..., Lₙ，假设它们同时到达。证明：按长度升序执行（即 SJF）时，平均周转时间最小。

### 推导

设作业按某种顺序执行，长度依次为 L₁, L₂, ..., Lₙ。

- 第 1 个作业的周转时间：T₁ = L₁
- 第 2 个作业的周转时间：T₂ = L₁ + L₂
- 第 3 个作业的周转时间：T₃ = L₁ + L₂ + L₃
- ...
- 第 n 个作业的周转时间：Tₙ = L₁ + L₂ + ... + Lₙ

总周转时间 = T₁ + T₂ + ... + Tₙ
           = n·L₁ + (n-1)·L₂ + (n-2)·L₃ + ... + 1·Lₙ

平均周转时间 = [n·L₁ + (n-1)·L₂ + ... + 1·Lₙ] / n

### 结论

总周转时间中，每个作业长度 Lᵢ 被乘以它的"权重" (n - i + 1)。为了让总和最小，应该让**最短的作业配最大的权重**，最长的作业配最小的权重。

即按 L₁ ≤ L₂ ≤ ... ≤ Lₙ 升序执行——这正是 SJF 的顺序。

### 公式

平均周转时间 = (1/n) · Σᵢ (n - i + 1) · Lᵢ

其中 L₁ ≤ L₂ ≤ ... ≤ Lₙ。
